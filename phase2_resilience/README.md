# フェーズ2：障害設計（壊れることを前提に作る）

> 参照：[Ch.3 Embracing Risk](https://sre.google/sre-book/embracing-risk/) / [Ch.13 Emergency Response](https://sre.google/sre-book/emergency-response/) / [Ch.14 Managing Incidents](https://sre.google/sre-book/managing-incidents/) / [Ch.15 Postmortem Culture](https://sre.google/sre-book/postmortem-culture/) / [Ch.22 Cascading Failures](https://sre.google/sre-book/addressing-cascading-failures/)

## 目標
「システムは必ず壊れる」という前提に立ち、壊れたときの影響を最小化する設計・対応・学習のサイクルを身につける。

## 1. リスクを受け入れる（Embracing Risk）

> [Chapter 3 - Embracing Risk](https://sre.google/sre-book/embracing-risk/)

### 100%の可用性は間違ったゴール

> "Extreme reliability comes at a cost: maximizing stability limits how fast new features can be developed."

99.99%と99.999%の差をユーザーは知覚できない。なぜならユーザーの手元には携帯の電波やWi-Fiなど、それ自体が99.9%未満の信頼性しかないコンポーネントが存在するからだ。

信頼性を上げるコストは線形ではなく、指数的に増加する：

```
99%   → 99.9%  : 比較的安価
99.9% → 99.99% : 100倍コスト
99.99%→ 99.999%: さらに100倍コスト
```

**SREのゴール：** 信頼性を最大化することではなく、ビジネスが受け入れられるリスクのレベルに合わせた信頼性を作ること。

### 可用性の計算方法

Googleが使うリクエストベースの計算式：

```
可用性 = 成功したリクエスト数 / 総リクエスト数
```

例：1日250万リクエストで、SLO 99.99%の場合、許容エラー数は250件。

### サービスのリスク許容度を決める問い

- ユーザーはどのレベルの可用性を期待しているか？
- このサービスは直接収益に結びついているか？
- 有料サービスか無料サービスか？
- 競合他社はどのレベルを提供しているか？
- エンタープライズ向けか、コンシューマー向けか？

## 2. 障害の種類と設計パターン

### 単一障害点（SPOF: Single Point of Failure）

1台のサーバー・1つのデータベース・1つのネットワーク経路がシステム全体の可用性を決める構造。

**対策：** 冗長化（N+1構成）、複数AZへの分散。

### カスケード障害（Cascading Failure）

> [Chapter 22 - Addressing Cascading Failures](https://sre.google/sre-book/addressing-cascading-failures/)

部分的な障害が正のフィードバックを生み、障害が連鎖・拡大していく現象。

**典型的なシナリオ：**

```
クラスタBが障害
→ クラスタAへ全トラフィックが集中（1.2倍の負荷）
→ クラスタAがリソース枯渇でクラッシュ
→ さらに他クラスタへ負荷が集中
→ 全クラスタがクラッシュ（サービス全断）
```

**カスケード障害の主な原因（SRE本より）：**

| 原因 | 内容 |
|------|------|
| サーバー過負荷 | 最も多い原因。負荷増加 → クラッシュ → さらなる負荷集中 |
| リソース枯渇（CPU） | リクエスト遅延 → キューイング → メモリ増大 → GCループ |
| リソース枯渇（メモリ） | キャッシュ縮小 → バックエンド負荷増大 → さらなるクラッシュ |
| GCデススパイラル（Java） | CPU不足 → リクエスト遅延 → RAM増大 → GC増大 → CPU不足 |

**重要な洞察：**  
カスケード障害が始まると、負荷を元の水準に戻しても回復しないことがある。サービスが10,000QPSで正常だったとして11,000QPSでカスケードが始まった場合、9,000QPSに下げても復旧しない。生き残ったサーバーが少なすぎて、復活したサーバーが即座に再クラッシュするからだ。

### サーキットブレーカー

電気のブレーカーと同じ発想。依存先サービスの障害を検知したら、リクエストを送るのをやめ「回路を切る」。

```
通常状態（Closed）
→ エラー率が閾値超え
→ オープン状態（Open）：すべてのリクエストを即エラーで返す
→ 一定時間後、ハーフオープン（Half-Open）：試験的にリクエストを通す
→ 成功したらClosed に戻る
```

**なぜ必要か：** 障害中の依存サービスにリクエストを送り続けると、タイムアウト待ちでスレッドが詰まり、自分のサービスも道連れになる。

### リトライとジッター

> "If at first you don't succeed, back off exponentially." — Dan Sandler, Google

リトライは単純にやると逆効果。すべてのクライアントが同時にリトライすると、障害から復旧しようとしているサーバーに再び過負荷をかける（**リトライストーム**）。

**正しいリトライ設計：**

```
指数バックオフ：1s → 2s → 4s → 8s → ...
ジッター追加  ：1s → 2.3s → 3.8s → 9.1s → ...（ランダムなずれ）
最大リトライ回数を設定する
```

> "Why do people always forget that you need to add a little jitter?" — Ade Oshineye, Google

### タイムアウト設計

タイムアウトを設定しないと、依存先がハングしたとき自分のリクエストも無限に待ち続け、スレッドが詰まる。

- **コネクションタイムアウト**：接続が確立するまでの上限
- **リードタイムアウト**：レスポンスが返るまでの上限
- **デッドライン伝播**：マイクロサービスでは上流から下流へタイムアウトを引き継ぐ

## 3. インシデント対応

> [Chapter 13 - Emergency Response](https://sre.google/sre-book/emergency-response/) / [Chapter 14 - Managing Incidents](https://sre.google/sre-book/managing-incidents/)

### インシデントの種類

| 種類 | 内容 | 例 |
|------|------|-----|
| テスト起因 | 本番環境でのテストが原因 | 負荷テストが予期せず本番トラフィックに影響 |
| 変更起因 | デプロイ・設定変更が原因 | 新機能リリース後にエラー率が急増 |
| プロセス起因 | 運用手順のミスが原因 | バッチ処理の順序を間違えてデータが壊れる |

### インシデント管理の構造

Googleの定義では、以下の役割を明確に分担する：

| 役割 | 責務 |
|------|------|
| **インシデントコマンダー（IC）** | 対応全体の指揮。手を動かさず判断に集中 |
| **オペレーション担当** | 実際の調査・修正作業 |
| **コミュニケーション担当** | 関係者への状況共有、ステータスページ更新 |

**インシデント宣言のタイミング：**
迷ったら宣言する。インシデントを宣言するコストより、宣言しないコストの方が大きい。

### オンコールの設計

- 8〜12時間のシフトで **最大2件** のイベント対応が適切（SRE本より）
- 2件を超えると調査が不十分になり、学習の機会が失われる
- 1件未満が続くようならオンコールは不要かもしれない

## 4. ポストモーテム（Postmortem）

> [Chapter 15 - Postmortem Culture](https://sre.google/sre-book/postmortem-culture/)

### ポストモーテムとは

障害の書面記録。以下を含む：
- 何が起きたかの詳細
- 影響範囲
- 対応のタイムライン
- 根本原因（複数ある場合は全て）
- 再発防止策

**ポストモーテムを書くトリガー（Googleの基準）：**
- ユーザーに見える形でのダウンタイム・劣化
- 任意の種類のデータロス
- オンコールエンジニアの手動介入（ロールバック、トラフィック切り替えなど）
- 解決に要した時間が閾値超え
- モニタリングの失敗（手動で問題を発見した場合）

### ブレームレス（Blameless）文化

> "Blameless postmortems are a tenet of SRE culture."

**犯人探しをしない** のがSREの鉄則。

- 人間は失敗する。システムは人間の失敗を防げるよう設計すべき
- 「誰がやったか」ではなく「なぜシステムがそれを防げなかったか」を問う
- 責任追及の文化があると、問題が隠蔽されるようになり、長期的に信頼性が下がる
- ブレームレスな文化は医療・航空業界で命を救ってきた実績がある

**やってはいけない例：**
> 「あのバックエンド全部書き直すべき！毎週壊れてもう限界！」

**ブレームレスな例：**
> 「バックエンドの書き直しをアクションアイテムにすることで再発を防げる。メンテナンスドキュメントも複雑なので、将来のオンコール担当のためになる」

### ポストモーテムのレビュー基準

- 主要なインシデントデータは記録されているか
- 影響範囲の評価は完全か
- 根本原因の掘り下げは十分か
- アクションプランは適切か、対応するissueの優先度は正しいか
- 関係するステークホルダーと共有したか

## 5. キャパシティプランニングの基礎

「今のリソースで将来の負荷を捌けるか」を事前に把握する取り組み。

### 考えるべき問い

- 現在のリソース使用率のトレンドはどうか
- 季節変動・イベント（大型セール、リリース）はあるか
- 1台落ちた状態（N-1）で今のトラフィックを捌けるか
- 2倍のトラフィックが来たとき何が最初に詰まるか（ボトルネック）

### リソース使用率の目標値

一般的に本番環境では以下を目安にする（サービスによって異なる）：

| リソース | 通常時の目標上限 | 理由 |
|----------|----------------|------|
| CPU | 60〜70% | スパイク時のヘッドルームを確保 |
| メモリ | 70〜80% | OOMKillを防ぐ |
| ディスク | 70〜80% | I/O遅延が始まる前に対処 |
