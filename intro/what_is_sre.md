# SREとは何か

> 参照：[Chapter 1](https://sre.google/sre-book/introduction/) / [Chapter 5](https://sre.google/sre-book/eliminating-toil/) / [Chapter 7](https://sre.google/sre-book/automation-at-google/)

## SREが生まれる前の世界

2000年代初頭、ソフトウェア開発の現場には大きな組織的摩擦があった。

**開発チーム（Dev）** の目標は「新機能を速くリリースすること」。  
**運用チーム（Ops）** の目標は「システムを安定させること」。

この2つは本質的に対立する。

```
開発「新機能をリリースしたい」
運用「リリースするたびに障害が増える。リリースを遅らせてほしい」
開発「それじゃビジネスが止まる」
運用「でも障害対応で夜中に叩き起こされるのはこちらだ」
```

運用チームは変化を嫌う。変化こそが障害の原因だからだ。開発チームは変化を求める。変化こそが価値だからだ。この構造的な対立は、多くの組織で「開発 vs 運用」という文化的断絶を生んだ。

---

## Googleでの誕生

2003年、GoogleのVPエンジニアリングである **Ben Treynor Sloss** は一つの問いを立てた。

> 「ソフトウェアエンジニアが運用チームを設計したらどうなるか？」

彼はこれを実践し、それが **SRE（Site Reliability Engineering）** の起源となった。

GoogleはこのアプローチをSRE本（*Site Reliability Engineering: How Google Runs Production Systems*、Betsy Beyer他編、O'Reilly、2016年）として公開し、業界全体に広まった。Ben Treynor Sloss 自身が Chapter 1 を執筆している。

**核心となる考え方（Chapter 1 より）：**

> 運用の問題をソフトウェアエンジニアリングで解く。

「人が手作業でやっていることをコードに置き換える」「障害を個人の失敗ではなくシステムの問題として扱う」。これがSREの哲学だ。

---

## SREが解決しようとした問題

### 問題1：「人が頑張る」運用の限界

従来の運用は属人的だった。

- ベテランが「なんとなく」異常を察知する
- 障害対応の手順が口頭で伝わる
- 特定の人がいないと夜中の障害に対応できない

これはスケールしない。サービスが10倍になっても、人を10倍雇えるわけではない。

SREはこれをコードと自動化で解く。監視・デプロイ・スケールアップ・障害対応の手順をすべてコードにする。

### 問題2：障害が「誰かのせい」になる文化

従来の運用では、障害が起きると犯人を探す。  
犯人が見つかると「気をつけます」で終わる。  
同じ障害が繰り返される。

SREは障害を**システムの問題**として扱う。「誰がミスをしたか」ではなく「なぜシステムがそのミスを防げなかったか」を問う。これが**ポストモーテム文化**だ。

### 問題3：開発と運用の目標が噛み合わない

SREはこれを**エラーバジェット**という概念で解決した。

「このサービスは月に43分まで落ちていい（SLO 99.9%）」と決める。  
バジェットが余っているなら開発チームは積極的にリリースできる。  
バジェットを使い切ったら、開発チームは新機能より信頼性改善に集中しなければならない。

これにより「開発 vs 運用」の対立が、**共通の数値を使った議論**に変わる。

---

## SREとDevOpsの違い

よく混同されるので整理する。

| | DevOps | SRE |
|--|--------|-----|
| **何か** | 文化・哲学・運動 | 具体的な実装方法・ロール |
| **目標** | 開発と運用の壁をなくす | 信頼性をエンジニアリングで担保する |
| **起源** | 業界全体のムーブメント | Google発の具体的プラクティス |
| **関係** | 抽象的な原則 | DevOpsの原則を具体化したもの |

SREはDevOpsの「どうやって実現するか」の一つの答えとも言える。

## SREが担う仕事の範囲

SREが「何をするロールか」は組織によって異なるが、Googleの定義を基にすると以下になる。

### 信頼性の定義と計測
- サービスのSLO（目標）を決める
- SLI（指標）を計測する仕組みを作る
- エラーバジェットを管理する

### オブザーバビリティ（可観測性）の構築
- ログ・メトリクス・トレーシングの基盤を作る
- 問題が起きたときに「何が・どこで・なぜ」を即座に分かるようにする

### 信頼性のための設計
- 単一障害点をなくす設計のレビュー
- サーキットブレーカー・リトライ・タイムアウトなどの障害設計
- キャパシティプランニング（将来の負荷に対してどう備えるか）

### 障害対応とポストモーテム
- インシデント対応の指揮
- 障害後の振り返り（根本原因分析）
- 再発防止策の実装

### トイルの削減
「トイル（Toil）」とはSREが特に重視する概念で、**手作業・繰り返し・自動化できるのにしていない作業**のこと。  
SREはトイルを減らすためにコードを書く。トイルへの対応が業務の50%を超えたら問題と見なす。

## 自動化の5段階

> 参照：[Chapter 5 - Eliminating Toil](https://sre.google/sre-book/eliminating-toil/) / [Chapter 7 - The Evolution of Automation at Google](https://sre.google/sre-book/automation-at-google/)

「トイルを自動化する」といっても、一気に完全自動化できるわけではない。自動化には段階がある。

### Stage 1：手動対応（No Automation）

```
障害発生 → 人が気づく → 人が調べる → 人が直す
```

手順書すらない状態。担当者の記憶と経験に依存する。スケールせず、夜中に人が叩き起こされる。

### Stage 2：手順書による標準化（Documented Manual Process）

```
障害発生 → 人が気づく → Runbookを開く → 手順通りに対応
```

「何をすべきか」が文書化され、誰でも同じ手順で対応できる。ただし実行するのはまだ人間。属人性は減るが、人が実行するコストとヒューマンエラーは残る。

### Stage 3：部分的な自動化（Partially Automated）

```
障害発生 → 人が気づく → スクリプトを実行する → 結果を確認して判断する
```

よくある対応の一部がスクリプト化されている。人はトリガーと最終判断を担う。対応が速くなりミスが減るが、人が起きていないと動かない。

### Stage 4：完全な自動化（Fully Automated）

```
障害発生 → システムが検知 → 自動で対応 → 人に通知（事後報告）
```

人の介入なしに問題が解決される。アラートではなく「対応済み通知」が届く（オートスケール、自動フェイルオーバーなど）。自動化のロジックが間違っていると被害が拡大するリスクもある。

### Stage 5：自律的なシステム（Autonomous / Self-healing）

```
問題が起きる前にシステムが予測して対処する
```

障害が起きる前に回避する。完全な自律は難しく、多くのシステムはStage 3〜4の間にある。

### 段階の使い方

重要なのは、**すべてを一気にStage 5にする必要はない**という点だ。

```
Stage 1 → 2：まず記録する。知識を組織に残す。
Stage 2 → 3：繰り返す作業をスクリプト化する。
Stage 3 → 4：人の判断が不要な部分を自動化する。
Stage 4 → 5：予測と予防に投資する。
```

### トイルの判定基準

以下に当てはまる作業はトイルであり、自動化の優先候補になる：

- [ ] 手作業で行っている
- [ ] 繰り返し発生する（週次、月次、障害のたびなど）
- [ ] 自動化できる（技術的に不可能ではない）
- [ ] ビジネス価値を直接生まない
- [ ] サービスの成長に比例して増える（スケールしない）

### SWEとして意識すること

自動化の段階はインフラだけの話ではない。コードを書く段階からStage 4・5を意識できる。

| 設計の判断 | 自動化との関係 |
|------------|----------------|
| ヘルスチェックエンドポイントを作る | Stage 4の自動検知を可能にする |
| グレースフルシャットダウンを実装する | 自動再起動時のデータ損失を防ぐ |
| 冪等なAPI設計にする | 自動リトライが安全にできる |
| 設定を環境変数で渡す | 自動スケール時に設定変更が不要になる |

## SWEとSREの違い

SWEとして開発経験があるなら、SREとの違いはこの1点に集約できる。

| | SWE | SRE |
|--|-----|-----|
| **関心の時間軸** | 「このコードは正しく動くか」 | 「このシステムは1年後も動き続けるか」 |
| **失敗への姿勢** | バグをなくす | 失敗を前提に設計する |
| **成功の定義** | 機能が動く | ユーザーが困らない |

SREはコードを書く。ただし「機能」ではなく「信頼性」を作るためのコードを書く。

---

## なぜSWEがSREを学ぶべきか

SREは「ロールではなく、SWEやインフラが持つべき視点」という捉え方もある。

自分が書いたコードが：
- 本番で何回エラーを出しているか
- どのくらいのレイテンシで動いているか
- メモリをどのくらい使っているか
- 1台のサーバーが落ちたときに動き続けるか

これを意識してコードを書けるSWEは、プロダクトの信頼性を根本から変える。
