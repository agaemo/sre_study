# フェーズ1：オブザーバビリティ（計測と可視化）

> 参照：[Chapter 4 - Service Level Objectives](https://sre.google/sre-book/service-level-objectives/) / [Chapter 6 - Monitoring Distributed Systems](https://sre.google/sre-book/monitoring-distributed-systems/)

## 目標
「システムの今の状態を数値で語れる」ようになる。
感覚ではなく、データをもとに判断する習慣を作る。

---

## 1. SLI / SLO / SLA / エラーバジェット

### 概念

| 用語 | 意味 | 例 |
|------|------|----|
| **SLI** (Service Level Indicator) | 計測する指標 | リクエスト成功率、P99レイテンシ |
| **SLO** (Service Level Objective) | SLIの目標値 | 成功率 99.9%、P99レイテンシ < 200ms |
| **SLA** (Service Level Agreement) | ユーザーとの契約 | SLO違反時に返金する約束 |
| **エラーバジェット** | 「許容できる障害量」の枠 | 月間ダウンタイム 43.8分（99.9%の場合） |

### エラーバジェットが重要な理由

エラーバジェットは「どれだけリスクを取れるか」の通貨。
- バジェットが余っている → 積極的にリリースできる
- バジェットを使い切った → リリースを止めて信頼性改善に集中する

これにより「開発速度 vs 安定性」の対立が、数値で議論できる問題になる。

### 計算例

```
月間 = 30日 = 2,592,000秒
SLO = 99.9%
エラーバジェット = 2,592,000 × 0.001 = 2,592秒 ≈ 43分
```

### 演習
- 自分が過去に触ったサービスのSLOを考えてみる
- 「このAPIのSLOは何%が妥当か？」を理由とともに書いてみる

## 2. Four Golden Signals（4つのゴールデンシグナル）

SRE本 Chapter 6 で定義されている、**最優先で計測すべき4つの指標**。

> "If you can only measure four metrics of your user-facing system, focus on these four."

| シグナル | 意味 | 計測例 |
|----------|------|--------|
| **Latency（レイテンシ）** | リクエストの処理時間 | P99レイテンシ < 200ms |
| **Traffic（トラフィック）** | システムへの需要量 | リクエスト数（RPS） |
| **Errors（エラー）** | 失敗したリクエストの割合 | 5xxエラー率 |
| **Saturation（飽和度）** | リソースの「詰まり具合」 | CPU使用率、メモリ使用率 |

### 各シグナルのポイント

**Latency**：成功したリクエストと失敗したリクエストのレイテンシは分けて計測する。エラーは速く返ってくることが多く、混ぜると実態が見えなくなる。

**Traffic**：サービスの種類によって単位が変わる。WebサービスならRPS、動画ストリーミングなら同時セッション数など。

**Errors**：HTTP 500のような明示的なエラーだけでなく、「200を返しているが中身が壊れている」ような暗黙的なエラーも計測する。

**Saturation**：リソースは100%に達する前に性能が劣化し始める。レイテンシの増加は飽和の予兆シグナルであることが多い。

この4つを計測してどれかが閾値を超えたらアラートを出せば、最低限のモニタリングは成立する。

## 3. レイテンシ・スループット・可用性

### 重要な計測値

| 指標 | 意味 | なぜ重要か |
|------|------|------------|
| **P50（中央値）** | リクエストの半分がこの時間以内 | 「平均的なユーザー体験」 |
| **P95** | 95%のリクエストがこの時間以内 | ほとんどのユーザーの体験 |
| **P99** | 99%のリクエストがこの時間以内 | ヘビーユーザー・複雑なケース |
| **P99.9** | 999/1000がこの時間以内 | SLO設計に使うことが多い |

**平均レイテンシを使ってはいけない理由**：外れ値に引っ張られ、最悪のユーザー体験を隠す。

### スループット vs レイテンシのトレードオフ

```
スループット = 単位時間あたりのリクエスト数（RPS）
レイテンシ   = 1リクエストにかかる時間

高負荷時：スループットを上げるとレイテンシが悪化することが多い
```

## 3. オブザーバビリティの3本柱

### ログ（Logs）
- 何が起きたかの記録
- 構造化ログ（JSON形式）が望ましい
- SREとして大切なのは「ログから問題を絞り込める設計」にすること

```json
{"timestamp": "2026-04-30T10:00:00Z", "level": "error", "service": "api", "request_id": "abc123", "error": "timeout", "duration_ms": 5001}
```

### メトリクス（Metrics）
- 時系列の数値データ
- 代表ツール：Prometheus、Datadog
- カウンター・ゲージ・ヒストグラムの3種類を理解する

| 種類 | 例 | 用途 |
|------|----|------|
| Counter | リクエスト総数 | 増加し続ける値 |
| Gauge | 現在のメモリ使用量 | 上下する値 |
| Histogram | レイテンシの分布 | パーセンタイル計算 |

**Cloud Runなどマネージドサービスでのメトリクス**

Cloud RunやLambdaのようなサーバーレス環境では、Prometheusのような「定期的にスクレイプしに来る」Pull型のメトリクス収集は相性が悪い。インスタンスがスケールゼロになったり、IPが変わったりするためPrometheusが安定してアクセスできないからだ。

こうした環境では以下のアプローチが使われる：

| アプローチ | 内容 |
|------------|------|
| **プラットフォーム組み込みのメトリクス** | Cloud RunはリクエストレイテンシやエラーレートをGoogle Cloud Monitoringに自動で記録する。コードの変更不要 |
| **OpenTelemetry（Push型）** | アプリ側からメトリクスをコレクターに送信（Push型）。PrometheusのPull型と異なり、スケールゼロ環境でも機能する |
| **Prometheus Pushgateway** | バッチ処理など短命なプロセスのメトリクスをPushgateway経由で収集する |

`/metrics` エンドポイントを実装してPrometheusに収集させる方式はサーバーが常駐している環境（KubernetesのPodなど）向けの設計であり、Cloud Runでも `/metrics` を実装すること自体は可能だが、Prometheusからの安定したスクレイプが困難なため、実際はCloud Monitoring + OpenTelemetryの組み合わせが主流になっている。

### トレーシング（Traces）
- 1リクエストがどのサービスをどの順で通ったかの記録
- マイクロサービス構成で「どこが遅いか」を特定するのに不可欠
- 代表ツール：Jaeger、Zipkin、OpenTelemetry

## 4. リソースの読み方

### CPU
- **使用率が高い ≠ 問題**（ただし継続的に100%はまずい）
- スロットリング（CPUが制限される状態）の方が危険
- Kubernetes環境：`requests`と`limits`の差が大きいと予測困難

### メモリ
- **GCによるSTW（Stop The World）**がレイテンシスパイクの原因になることが多い
- OOMKill（メモリ不足でプロセスが強制終了）は可用性に直結
- メモリリークの検出：時系列グラフで単調増加していないか確認

### ネットワーク
- レイテンシの内訳：アプリ処理時間 + ネットワーク往復時間（RTT）
- パケットロス・再送が増えているとTCPレイテンシが急増する

### ディスク
- I/Oがボトルネックになるとレイテンシが数十〜数百ms単位で悪化
- `iowait`が高いときはディスクが詰まっている
